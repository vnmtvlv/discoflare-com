## Backups

Cloudflare deployments separate storage by responsibility:

- D1 contains durable workspace facts and message history.
- R2 contains attachment bytes.
- Durable Objects contain live coordination state, not the durable history backup.
- KV contains temporary connection tickets, not message history.

A recoverable workspace-data backup needs both D1 and R2. Exporting only the database does not preserve attachments, and copying only R2 does not preserve the records that authorize and describe those objects.

The owner can create the same streaming TAR in two ways from **Workspace Settings → Backups**: download it to the current device, or upload it manually to a separately configured S3-compatible bucket. Device downloads may be slow and require the browser to remain connected. The bucket destination uses owner-supplied Endpoint, Region, Bucket, Prefix, Access Key ID, and Secret Access Key values; the secret is encrypted using `AUTH_SECRET` and never returned by the API.

Use a private destination bucket separate from the installation's live R2 files bucket. The guided installer still does not create an automatic backup before an upgrade. The manual archive excludes Worker environment secrets, KV tickets, Durable Object live state, running Agent turns, and external RealtimeKit data. Preserve `AUTH_SECRET` and deployment configuration separately; configure independent infrastructure backups when the workspace requires a stronger recovery policy.

## Upgrades

Owners of guided installations can open **Workspace Settings → Updates**. Discoflare compares the installed version with stable GitHub Releases and sends the owner to a release-pinned upgrade on `discoflare.com`. After Cloudflare OAuth, the installer finds the existing Worker by hostname, keeps its bound D1, R2, and KV resources, and updates it in place.

The installer reads the migration history from the existing D1 binding and applies every pending release migration in filename order. A migration and its history marker run in the same D1 batch; any failed or missing marker stops the deployment. GitHub/Workers Builds operators must update their fork, apply migrations, and deploy manually. After either update path:

1. Confirm the deployed application and Worker versions match the target release.
2. Request `/api/setup/health` and verify `ok: true`, `ready: true`, and `migrated: true`.
3. Sign in through a new browser session.
4. Read an existing message and attachment.
5. Send a new message and upload a new attachment.
6. Run an Agent Task if the release changed the Agent execution plane.

::docs-verification{title="An update is complete only after old and new data both work"}
Reading existing data proves compatibility with persisted state. Creating new data proves the updated write path. Test both before calling the rollout complete.
::

## Delete a server

The Owner can open **Workspace Settings → Danger Zone** to permanently delete a managed Discoflare server. Discoflare offers the Backups section first, but does not require a backup. Continuing creates a 15-minute, one-use authorization and opens the installer with a temporary Cloudflare connection. The installer finds the marked Worker by its exact hostname and requires the full server address to be typed before enabling deletion.

Deletion removes the Worker and Durable Object state, the managed D1 database, live R2 bucket, KV namespace, Workflow, Container application, Access applications, optional custom Worker domain, and email bindings owned by that installation. A separately configured S3 backup bucket is outside the installation and is never deleted. Shared zone-wide Email Routing configuration and unrelated DNS or email rules are preserved.

Manually deployed Workers must be removed from the Cloudflare dashboard. Discoflare does not automatically delete their bindings because the same D1, R2, or KV resource may be shared with another operator-managed service.
