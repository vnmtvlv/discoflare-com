The guided installer at [discoflare.com/deploy](/deploy) provisions Discoflare directly into your Cloudflare account. It uses a temporary OAuth session for provisioning; the installed Worker does not retain the Cloudflare access token.

## Before you begin

You need:

- a Cloudflare account with Workers Paid enabled;
- an email address for the first workspace owner; and
- an active DNS zone only if you want a custom application hostname or workspace mail.

The installer stops instead of replacing a hostname attached to another Worker, non-Cloudflare MX records, or another enabled catch-all email route.

## 1. Connect the account

Open [Deploy Discoflare](/deploy), select **Connect Cloudflare**, approve the requested permissions, and return to the installer.

The OAuth consent includes Access plus email-routing and email-sending permissions because those choices are made after account discovery. Turning **Custom domain** or **Workspace email** off prevents the installer from using the corresponding APIs, but it does not narrow the already-approved OAuth scope.

Select the account that will own the workspace. Select an active domain only when a domain-backed option is enabled.

::docs-verification{title="Verify account discovery"}
The installer must list the expected Cloudflare account and active zone. If either is missing, do not continue with a different account; correct the Cloudflare membership or zone status first.
::

## 2. Describe the workspace

Choose:

- a Worker name;
- the public workspace name;
- Cloudflare Access email codes or Discoflare-owned accounts;
- any additional email addresses allowed by the initial Access policy;
- whether to add a custom domain and, if enabled, the application subdomain;
- whether to enable workspace email and, if enabled, its subdomain and first mailbox;
- invite-only or open registration when using Discoflare accounts; and
- the first owner's email address.

These choices become deployment configuration. They are not inferred from the marketing site repository.

## 3. Install

Select **Install or update**. The installer loads a pinned Discoflare release, provisions its bindings, configures Cloudflare Access by default, enables any selected domain and email routing, deploys the Worker, and returns the workspace URL. The Discoflare-account alternative returns a private owner-setup link.

::docs-verification{title="Verify the installer result"}
The page must show **Installed Discoflare _version_** or **Updated to Discoflare _version_** and provide a workspace link. Treat an OAuth redirect, successful build, or created Worker by itself as partial progress, not completed installation.
::

## 4. Check platform readiness

Before creating the owner, open the health endpoint on the workspace origin:

```bash
curl -fsS https://chat.example.com/api/setup/health
```

For a fresh Access installation before the Owner first opens it, the response should include:

```json
{
  "ok": true,
  "authMode": "access",
  "ready": false,
  "migrated": true,
  "ownerSetup": false
}
```

`ok: true` proves the database binding exists and migrations completed. It does not mean owner setup is finished.

## 5. Create the workspace owner

With the default Access mode, open the workspace URL and enter the one-time code Cloudflare sends to the Owner email. The verified first visit creates the Owner and workspace together. Additional addresses entered during deployment can sign in afterwards; later allowlist changes are made in the Cloudflare Access application policy.

With Discoflare accounts, open the private setup link returned by the installer. The claim is carried in the URL fragment and removed from the address bar before it is submitted. Create the owner name and password.

The owner and workspace are created together before the workspace is marked ready. When workspace email is enabled, the first mailbox is provisioned during the same setup. The claim is single-use by state: after setup, another claim attempt is rejected.

::docs-verification{title="Verify owner setup"}
Reload `/api/setup/health`. It should now report `ok: true`, `ready: true`, and at least one user. Then sign out and sign back in with the owner credentials; this proves more than an existing browser session.
::

## 6. Run workspace checks

Perform one observable check for each capability you plan to use:

1. Create a channel and send a message.
2. Reload the page and confirm the message persists.
3. Upload a small attachment and download it again.
4. If using Access, test one allowed and one unlisted address in private browser windows.
5. If using Discoflare accounts, test the selected registration or invite policy.
6. Create an Agent and a Task only after the Sandbox image has had several minutes to provision.

If the first Agent run reports that the Sandbox is unavailable immediately after deployment, wait for provisioning and retry. Chat readiness and Agent Container readiness are separate checks.

## Optional integrations

Configure authentication methods in **Workspace Settings → Authentication** and RealtimeKit in **Workspace Settings → Huddles**. The Huddles screen includes a read-only connection test. Text chat works without RealtimeKit.

Deployment-managed provider credentials override credentials saved in the workspace UI and appear as managed by deployment. See [Environment variables](/docs/configuration/environment-variables).

## Manual GitHub deployment

The **Deploy with GitHub** option is for operators who want to own a repository fork and Workers Builds configuration. It is not another guided installer. The button transfers the public source to Cloudflare, but you must manually create or select the storage resources, adapt `wrangler.jsonc`, configure bindings and secrets, choose the build and deploy commands, attach the hostname, configure optional email routing and providers, apply migrations, create the first-owner setup claim, and run the readiness checks above.

Use `pnpm run build` as the Workers Builds build command and `pnpm run deploy:built` as the deploy command. Follow the [application deployment guide](https://github.com/vnmtvlv/discoflare/blob/main/docs/deployment.md) for the current resource checklist. Do not reuse the public sandbox's account-specific resource IDs, names, or hostname in another account.

::docs-verification{title="A GitHub build is only one layer of deployment evidence"}
Record the target resource IDs, successful D1 migration, deployed Worker version, hostname, `/api/setup/health` response, owner setup, browser realtime, attachment persistence, and Agent Task result separately.
::
